# 카페 판매·재고·비용 관리 1차 개발 계획

**EPIC 3개, User Story 14개**로 진행한다.

- EPIC: 함께 완성해서 실제로 사용해 볼 수 있는 작업 묶음.
- User Story: 사용자가 한 가지 목적을 달성하는 기능 단위.
- 작성일: 2026-10-12
- 상태: 사용자가 제시된 계획의 저장을 요청함. 미정 계산 기준과 저장 방식은 별도 결정 필요.
- 기준 문서: `01_PRD.md`, `02_FRD.md`, `03_TRD.md`와 `../design/`의 시안.

진행 상태(2026-10-12): EPIC 1 로컬 구현·개발자 검사 완료·사용자 확인 대기(EPIC 미완료), EPIC 2·3 미착수. 사용자 테스트 통과 기록은 아직 없다. 상세 결과는 `05_테스트결과.md`에서 관리한다.

## 1. 전체 작업 순서와 나눈 이유

| 순서 | EPIC | Story 수 | 완료 후 확인할 결과 |
| --- | --- | ---: | --- |
| 1 | 판매를 기록하고 메뉴 수익성 확인하기 | 4개 | 판매 입력·수정·삭제와 메뉴별 수익성 확인 |
| 2 | 비용과 재료 변화를 기록하고 손익 확인하기 | 5개 | 비용을 반영한 손익, 입고·폐기 기록 확인 |
| 3 | 재고 상태를 확인하고 기록을 가져오고 보호하기 | 5개 | 실사·부족 재료 확인, 엑셀 가져오기, 백업·복원 |
| 합계 | 3개 EPIC | 14개 | 핵심 흐름 전체 사용 가능 |

기초 정보가 있어야 판매 원가를 계산할 수 있으므로 EPIC 1을 먼저 진행한다. 그 판매 기록에 비용과 재료 변화를 연결하는 EPIC 2를 완성하고, 마지막으로 실사·부족 판단과 파일 처리를 연결한다. 엑셀 가져오기는 직접 입력의 검사·저장 기능을 재사용하고, 백업·복원은 모든 기록 구조가 준비된 뒤 구현한다.

판매 수정·삭제는 잘못된 판매를 바로잡는 목적, 양식 다운로드·파일 가져오기는 판매를 한꺼번에 등록하는 목적으로 각각 묶었다. 백업과 복원은 목적과 오류 위험이 달라 별도 Story로 나눴다.

문서에 남아 있는 저장 방식·원가·비용 배분·실사·부족 판단 등의 미정 사항은 유지한다. 아래의 계산 검사는 합의한 계산 기준과 별도로 계산한 기대값을 대조하며, 기준이 미정인 기능을 완료 처리하지 않는다.

## 2. EPIC 1 — 판매를 기록하고 메뉴 수익성 확인하기

**포함 Story: S01~S04, 4개**

기초 정보와 실제 저장 기능부터 만들고, 판매 기록을 메뉴 분석에 연결한다. 판매 시안은 확정된 날짜·메뉴·채널별 합계 방식에 맞춘다.

### S01. 분석에 필요한 기초 정보 준비하기

- 사용자가 할 수 있는 일: 메뉴·재료·가격·레시피·시작 재고를 준비하고 필요한 정보를 수정한다.
- 자동 검사: 메뉴와 재료 연결, 구매용량과 사용량의 단위, 가격 적용일, 빈칸과 0 구분, 저장 후 다시 읽은 값의 일치를 검사한다. 잘못된 연결·단위·용량을 정상 원가로 처리하지 않는지 확인한다.
- 화면 확인 행동과 예상 결과: 메뉴에 재료와 사용량을 연결하고 다시 접속한다. 저장한 내용이 유지되어야 한다. 연결 정보를 빠뜨리면 계산에 필요한 정보가 부족하다는 안내가 나와야 한다.

### S02. 판매 기록 입력하기

선행: S01

- 사용자가 할 수 있는 일: 날짜·메뉴·판매채널별 판매 합계를 입력하고 저장된 목록을 확인한다.
- 자동 검사: 순매출, 채널별 원가·재료 사용량, 잘못된 숫자·날짜, 연속 저장에 따른 중복, 저장 실패를 검사한다. 원가 누락 판매는 결정한 정책대로 처리하는지 확인한다.
- 화면 확인 행동과 예상 결과: 아메리카노 매장 판매 10잔을 입력한다. 목록에 한 번만 나타나고 다시 접속해도 유지되어야 한다. 잘못된 수량을 입력하면 이유가 표시되고 저장되지 않아야 한다.

### S03. 잘못된 판매 기록 바로잡기

선행: S02

- 사용자가 할 수 있는 일: 판매 기록을 찾아 수정하거나 잘못 입력한 기록을 삭제한다.
- 자동 검사: 변경 전 영향을 제거하고 변경 후 값만 반영하는지, 날짜·채널 변경, 삭제 취소, 삭제 확정, 저장 실패 시 기존 기록 유지 여부를 검사한다.
- 화면 확인 행동과 예상 결과: 판매 10잔을 8잔으로 수정하면 목록의 수량과 금액이 바뀌어야 한다. 삭제를 취소하면 유지되고, 확정하면 사라져야 한다. 완성된 분석 화면에도 같은 변경이 반영되어야 한다.

### S04. 메뉴별 수익성과 원가 근거 확인하기

선행: S01~S03

- 사용자가 할 수 있는 일: 기간과 메뉴를 선택해 판매량·매출·원가·메뉴 이익과 재료별 원가 근거를 확인한다.
- 자동 검사: 할인·채널·가격 적용일·당시 원가·수수료의 합의 기준을 대조한다. 매출 0과 원가 누락을 정상 이익률로 표시하지 않는지, 수정·삭제 후 집계가 일치하는지 검사한다.
- 화면 확인 행동과 예상 결과: 입력한 메뉴를 선택하면 판매 기록과 분석 수량·금액이 일치해야 한다. 원가 상세에서 사용 재료와 비용 근거를 볼 수 있어야 한다. 계산할 수 없는 항목은 0원 이익으로 표시되면 안 된다.

### EPIC 1 완료 기준

기초 정보를 준비하고 판매를 입력·수정·삭제한 뒤 메뉴 수익성을 실제 화면에서 확인할 수 있어야 한다. 저장 후 다시 접속해도 자료가 유지되고, 오류·계산 불가 상태를 구분해야 한다. 화면의 예시 숫자로 완료 처리하지 않는다.

## 3. EPIC 2 — 비용과 재료 변화를 기록하고 손익 확인하기

**포함 Story: S05~S09, 5개**

EPIC 1의 판매와 원가를 바탕으로 비용을 연결한다. 재료 입고·폐기는 서로 다른 기록 목적이므로 별도로 구현한다.

### S05. 비용 기록 입력하기

선행: EPIC 1의 저장·검증 구조

- 사용자가 할 수 있는 일: 운영 비용을 입력하고 비용 목록에서 확인한다.
- 자동 검사: 금액·날짜·필수 입력, 합의한 비용 반영 방식, 월 계획과 일별 비용의 중복 반영 방지, 저장 실패를 검사한다.
- 화면 확인 행동과 예상 결과: 비용 한 건을 등록하면 목록에 한 번 나타나고 다시 접속해도 유지되어야 한다. 금액이 잘못되면 해당 입력칸에 오류 이유가 표시되어야 한다.

### S06. 잘못된 비용 기록 바로잡기

선행: S05

- 사용자가 할 수 있는 일: 비용을 찾아 수정하거나 잘못 입력한 기록을 삭제한다.
- 자동 검사: 기존 비용을 중복으로 남기지 않는지, 기간 변경·삭제·취소·저장 실패의 영향을 검사한다.
- 화면 확인 행동과 예상 결과: 비용 금액을 수정하면 목록과 합계가 바뀌어야 한다. 삭제 취소 시 유지되고 확정 시 제외되어야 한다. S07 완료 후 손익에도 같은 변경이 반영되어야 한다.

### S07. 기간별 판매 실적과 매장 손익 확인하기

선행: S04~S06

- 사용자가 할 수 있는 일: 합의한 1차 기간 범위에서 판매 실적·비용·매장 손익을 확인한다. 현재 문서는 일·월을 우선 제안한다.
- 자동 검사: 판매·원가·수수료·비용을 합의 기준대로 한 번씩 반영하는지 대조한다. 기간 경계, 부분 기간, 미래·미마감 날짜, 매출 0, 원가 누락을 검사한다.
- 화면 확인 행동과 예상 결과: 판매와 비용이 있는 날짜를 선택하면 기록과 일치하는 손익이 나와야 한다. 월 조회에는 포함 기간이 표시되어야 한다. 미마감 날짜는 확정된 판매 0처럼 보이면 안 된다.

### S08. 재료 입고 기록하기

선행: S01~S03

- 사용자가 할 수 있는 일: 재료가 들어온 날짜와 수량을 기록한다.
- 자동 검사: 단위 환산, 입고 증가, 시작 재고와 판매 사용량 연결, 과거 날짜 입력, 저장 실패·중복 저장을 검사한다.
- 화면 확인 행동과 예상 결과: 우유를 입고하면 입고 기록과 추정 잔량이 합의된 단위로 증가해야 한다. 다시 접속해도 유지되어야 한다. 잘못된 단위는 정상 반영되면 안 된다.

### S09. 재료 폐기 기록하기

선행: S08의 재고 집계 구조

- 사용자가 할 수 있는 일: 버린 재료의 날짜·수량·사유를 기록한다.
- 자동 검사: 폐기량의 차감 방향, 판매 사용량과 중복 차감 방지, 단위·입력 오류, 음수 잔량 처리, 합의한 폐기 비용 반영을 검사한다.
- 화면 확인 행동과 예상 결과: 우유를 폐기하면 입고와 반대 방향으로 잔량이 줄어야 한다. 음수 잔량이 발생하면 임의로 0으로 바꾸지 않고 확인이 필요한 상태를 보여야 한다.

### EPIC 2 완료 기준

판매·비용을 근거로 기간 손익을 확인하고, 입고·폐기를 실제 저장하여 재료 잔량에 반영할 수 있어야 한다. 기존 판매·비용을 변경해도 관련 결과가 일치해야 한다. 입고 대금과 소진 원가 등 같은 비용이 이중 반영되지 않아야 한다.

## 4. EPIC 3 — 재고 상태를 확인하고 기록을 가져오고 보호하기

**포함 Story: S10~S14, 5개**

재고 기록을 실측과 연결하고, 검증된 입력 기능을 파일 처리에 재사용한다. 마지막으로 전체 기록의 백업·복원을 완성한다.

### S10. 실제로 센 재고 기록하기

선행: S08~S09

- 사용자가 할 수 있는 일: 재료를 실제로 센 수량을 기록하고 같은 시점의 추정 잔량과 비교한다.
- 자동 검사: 실측 총수량을 입고량처럼 더하지 않는지, 실측 0, 기준 시점, 동일 날짜 순서, 과거 기록 변경을 합의된 실사 정책대로 처리하는지 검사한다.
- 화면 확인 행동과 예상 결과: 추정 1,000ml인 재료의 실측수량을 900ml로 입력하면 같은 시점의 차이 −100ml를 확인할 수 있어야 한다. 잔량을 조정할지는 합의한 정책에 따라 표시되어야 한다.

### S11. 남은 재료와 부족 여부 확인하기

선행: S10 및 부족 판단 기준 합의

- 사용자가 할 수 있는 일: 재료별 잔량·최근 실측·부족 여부를 확인하고 필요한 재료를 찾는다.
- 자동 검사: 시작 재고부터의 누적, 판매·입고·폐기·실사 반영, 부족 기준의 경계값, 누락된 레시피·시작 재고·기준을 검사한다.
- 화면 확인 행동과 예상 결과: 판매나 폐기를 기록하면 잔량과 부족 상태가 갱신되어야 한다. 기준이 없으면 ‘판단 불가’, 잔량 근거가 부족하면 ‘확인 필요’로 구분되어야 한다. 발주량 추천은 포함하지 않는다.

### S12. 엑셀로 판매 기록 한꺼번에 입력하기

선행: S02~S04, S07, S11 및 가져오기 정책 합의

- 사용자가 할 수 있는 일: 판매 양식을 내려받아 작성하고, 파일의 검사 결과를 확인한 뒤 판매를 가져온다.
- 자동 검사: 내려받은 양식의 재입력, 날짜·숫자·메뉴 연결, 빈 행, 오류·중복·재시도 정책, 저장 중 실패를 검사한다. 가져온 판매가 분석·손익·재고에 한 번씩 반영되는지 대조한다.
- 화면 확인 행동과 예상 결과: 정상 행과 오류 행이 섞인 파일을 선택하면 원본 행 번호와 오류 이유가 나와야 한다. 미리보기만으로는 저장되지 않고, 실행 후에는 합의한 정책에 따른 실제 반영 건수와 결과가 일치해야 한다.

### S13. 전체 기록 백업하기

선행: 모든 기록 구조 준비 및 백업 형식 합의

- 사용자가 할 수 있는 일: 현재 저장된 전체 기록을 백업 파일로 내려받는다.
- 자동 검사: 판매·비용·재고·기초 정보·필요한 달력·확정 정책의 포함 여부, 같은 시점의 일관성, 버전 정보, 생성 실패를 검사한다.
- 화면 확인 행동과 예상 결과: 백업을 실행하면 실제 파일이 내려받아지고 포함 범위와 생성 시점을 확인할 수 있어야 한다. 판매 양식이나 일부 화면의 표를 전체 백업이라고 표시하면 안 된다.

### S14. 백업 파일로 기록 복원하기

선행: S13 및 복원 교체·병합 정책 합의

- 사용자가 할 수 있는 일: 백업 파일의 내용과 영향을 확인한 뒤 기록을 복원한다.
- 자동 검사: 백업 전후 기록과 계산 결과의 일치, 연결·버전 오류, 손상된 파일, 복원 중 실패, 합의한 교체·병합 정책을 검사한다.
- 화면 확인 행동과 예상 결과: 백업 후 시험용 기록을 변경하고 복원하면 선택한 정책에 맞는 목록·손익·재고를 확인할 수 있어야 한다. 잘못된 파일이나 복원 실패 때문에 현재 자료가 지워지면 안 된다.

### EPIC 3 완료 기준

실제 재고와 부족 상태를 확인하고, 엑셀 판매 입력을 핵심 분석 흐름에 연결할 수 있어야 한다. 실제 백업 파일을 만들고 복원하여 기록과 계산 결과의 일치를 확인해야 한다. 이때 전체 핵심 흐름을 처음부터 다시 검사한다.

## 5. 모든 Story에 적용할 완료 조건

저장과 검사를 마지막 EPIC까지 미루지 않는다. 각 Story는 다음을 포함해야 완료다.

- 실제 입력·저장·재조회가 작동하고 다시 접속해도 기록이 유지된다.
- 계산은 합의된 기준으로 기대값과 대조한다. 미정 기준이나 예시 숫자를 정답으로 사용하지 않는다.
- 잘못된 입력, 저장 실패, 취소, 중복 실행에 대한 기본 처리를 확인한다.
- 해당 시안을 실제 자료에 연결하고, 필요한 입력·오류 화면이 없는 부분은 보완한다.
- Story 자체의 자동 검사와 사용자의 화면 확인을 모두 통과한다.
- 앞서 완성한 기능에 영향을 주는 변경은 관련 검사도 다시 실행한다.

GitHub 보관·자동 검사·Vercel 시험 배포는 각 EPIC의 공통 작업으로 수행한다. 최종 운영 배포 후에도 입력·조회·파일·저장·복원을 확인한다. 별도의 ‘화면만 만들기’ 또는 ‘저장 기능은 나중에 붙이기’ EPIC은 두지 않는다.

PRD의 기획 30분·화면 설계 20분·개발 125분·검사 40분·배포 25분 목표는 유지한다. 다만 미정 정책과 사용 환경이 남아 있어 현재 계획의 전체 구현을 4시간 내 보장할 수는 없다. 검사나 필수 기능을 몰래 줄여 시간을 맞추지 않는다.

이 계획의 저장은 미정 계산 기준이나 저장 방식을 함께 확정하는 것으로 처리하지 않는다.
