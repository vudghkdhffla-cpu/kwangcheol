## 1. 적용 범위와 확정 상태

### 확정된 사항

- 코드는 GitHub에 보관하고 웹 프로그램은 Vercel에 배포한다.
- 판매 기록 단위는 **날짜·메뉴·판매채널별 합계**다(FRD D01, 사용자 선택 A).
- 기초 정보 준비 → 판매 입력 → 메뉴 수익성 → 기간 손익·재료 잔량 → 기록 수정·저장·백업·복원의 흐름을 유지한다.
- 부족한 계산 근거를 0으로 대체하거나 미래·미마감 날짜를 확정 실적처럼 표시하지 않는다.

### 기술로 대신 결정하지 않는 사항

PRD의 한 매장·한 명·4시간 목표와 일·월 중심 1차 범위는 제안 상태다. FRD D02~D10 및 C01~C10 계산 제안은 확정되지 않았다. 특히 원가 누락 판매 저장, 과거 원가 변경, 수수료·폐기 비용 반영, 비용 배분, 실사 조정, 부족 기준, 엑셀 중복·오류 처리, 기간 경계, 저장·복원 방식은 기술 선택으로 확정하지 않는다.

이 문서의 기본 설계는 **같은 컴퓨터·같은 브라우저에 기록을 저장하는 A안**을 전제로 한 추천안이다. 사용 환경 답변 전에는 승인된 제한으로 취급하지 않는다. 서버 저장을 선택하면 12장의 구조 변경과 시간 재검토가 필요하다.

### 1차 기능 연결

| FRD | 기능 | 기술 담당 부분 |
| --- | --- | --- |

## 2. 기술 선택

업무 정책과 관계없이 선택 가능한 화면·빌드 도구는 다음으로 정한다. 저장 도구는 A안 선택을 조건으로 한다. 외부 서비스를 많이 연결하지 않고 작은 데이터 규모에서 핵심 흐름을 검증하기 위한 구성이다.

| 기술 | 쉬운 설명 | 사용 목적·선정 이유 |
| --- | --- | --- |
| React + TypeScript | 화면을 작은 조각으로 만들고 잘못된 자료 형식을 개발 중 확인하는 도구 | 목록·입력창·기간 선택을 재사용하고 기록 타입을 명확히 함 |
| Vite | 코드를 실행·배포 파일로 묶는 도구 | 작은 웹 프로그램의 개발·정적 배포에 적합 |
| CSS와 디자인 변수 | 색·간격·글꼴을 공통 값으로 관리 | 시안 스타일을 가져오면서 실행 중 외부 스타일 스크립트 의존 제거 |
| IndexedDB + Dexie, A안 조건부 | 브라우저 안의 구조화된 기록 저장소와 접근 도구 | 판매·재고·비용을 기록별로 보관하고 여러 변경을 함께 저장 |
| Zod | 입력과 파일 구조가 규칙에 맞는지 검사하는 도구 | 직접 입력·가져오기·복원이 같은 검증 규칙을 사용 |
| SheetJS Community Edition | 엑셀 파일을 읽고 만드는 도구 | 판매 XLSX 양식 생성과 가져오기 구현 |
| decimal.js | 소수 계산 오차를 줄이는 도구 | 가격÷구매용량, 재료 사용량 등 계산의 정밀도 보존 |
| Vitest + fake-indexeddb | 계산과 저장을 자동 검사하는 도구 | 핵심 계산·일괄 저장 실패·복원 검증 |
| Playwright | 실제 브라우저를 조작해 검사하는 도구 | 핵심 흐름·파일 다운로드·다시 열기 검증 |
| GitHub + Vercel | 코드 보관 장소와 웹 배포 장소 | 변경 내역 보관, 시험 배포 확인 후 운영 배포 |

Vercel은 Vite 배포를 지원한다. [Vercel의 Vite 안내](https://vercel.com/docs/frameworks/frontend/vite)

개발 실행 환경은 Node.js 22.x 중 Vite 요구 조건을 만족하는 패치 버전으로 맞추고 로컬·자동 검사·Vercel에서 동일하게 사용한다. Vite 공식 요구는 Node.js 20.19+ 또는 22.12+다. 실제 채택 버전은 구현 시작 시 지원·보안 상태를 확인해 고정한다. [Vite 시작 안내](https://vite.dev/guide/)

라이브러리 정확한 버전은 구현 때 확인한 호환 버전으로 잠금 파일에 고정하고 `npm ci`로 동일 설치한다. SheetJS는 공개 npm의 `xlsx`가 오래된 버전일 수 있으므로 공식 배포 경로를 사용하고 검증한 버전·출처를 기록한다. 사용 중 브라우저가 외부 CDN에서 라이브러리를 실행하도록 하지 않고 빌드에 포함한다. [SheetJS 설치 안내](https://docs.sheetjs.com/docs/getting-started/installation/frameworks/)

## 3. 프로그램 구조와 자료 흐름

```text
GitHub: 코드·문서·가상 검사 자료
    ↓ 검사 및 빌드
Vercel: HTML·CSS·JavaScript 제공
    ↓ HTTPS로 프로그램 접속
사용자 브라우저
    화면/입력 → 공통 검증 → 업무 처리 → IndexedDB(A안)
                                    ↓ 저장된 자료 조회
                              공통 계산 → 화면 결과
    판매 XLSX → 파일 해석 → 공통 검증 → 미리보기 → 승인된 반영
    백업 JSON ← 저장 자료의 일관된 복사
    복원 JSON → 구조/연결 검사 → 영향 확인 → 승인된 복원
```

화면은 저장소를 직접 수정하지 않는다. 업무 처리 부분이 입력 검사·저장·계산 결과 갱신을 담당한다. 계산 코드는 화면이나 엑셀 처리 코드에 흩어놓지 않는다. 서버 API는 A안에 필요하지 않다. 따라서 Vercel 함수의 파일이나 GitHub에 매장 기록을 저장하지 않는다.

구현 파일 구조:

| 위치 | 역할 |
| --- | --- |
| `src/pages/` | 판매·메뉴 분석·기간 손익·재고·비용·백업/기초 화면 |
| `src/components/` | 공통 목록·입력·오류·확인창·기간 선택 |
| `src/domain/` | 자료 타입, 승인된 업무 규칙, 계산 함수 |
| `src/application/` | 기록 입력/변경, 가져오기, 백업·복원 처리 순서 |
| `src/storage/` | 저장소 접근, 버전 변경, 일괄 저장 |
| `src/files/` | XLSX·백업 형식 해석과 생성 |
| `src/workers/` | 필요할 때 파일 해석을 별도 작업으로 실행 |
| `src/styles/` | 시안의 색·간격·표·모달 공통 스타일 |
| `tests/`, `docs/` | 핵심 검사와 요구사항·사용/복구 안내 |

6개 화면 이동은 같은 웹 문서 안의 상태 이동으로 구현한다. 별도 주소가 필요하면 해시 방식(`#sales` 등)을 사용해 새로고침 시 Vercel 경로 오류를 피한다. 화면 이동·표 검색은 FRD의 기능이며 새 사용 흐름을 만들지 않는다.

## 4. 데이터 구조와 저장

### 저장 대상

| 저장 묶음 | 주요 내용 | 연결·보존 규칙 |
| --- | --- | --- |
| 자료 정보 | 매장 표시명, 출처, 통화·금액 기준, 기록 기간 | 가상 자료와 실제 자료 구분 |
| 메뉴·재료·공급사 | ID·이름·분류·단위·구매 규격 | 이름 대신 ID로 연결. 없는 필드 임의 생성 금지 |
| 레시피 | 메뉴ID·재료ID·사용량·단위·채널 제한·버전 | 포장 전용 구분과 기존 버전 보존 |
| 가격 이력 | 재료ID·적용일·구매가격·용량 | 당시 가격과 최신 가격 분리 |
| 판매 | ID·일자·메뉴ID·채널·수량·단가·할인·순매출·수수료·당시 원가·레시피 버전 | 날짜·메뉴·채널은 검색 키. 같은 키를 자동 중복으로 단정하지 않음 |
| 비용·월 계획 | 기록ID·일자/월·분류·금액·반영 근거 | 월 계획과 기존 일별 배분은 같은 비용의 서로 다른 표현임을 보존 |
| 시작 재고 | 재료ID·기준일·수량·단위 | 조회 월 시작보다 앞선 재고 움직임 포함 |
| 재고 사건 | ID·일자·재료ID·유형·증감·실측수량·가격/공급사/사유 | 증감수량과 실제 센 총수량 분리 |
| 영업달력 | 일자·영업여부·마감여부·기존 메모 | 미래·미마감 날짜 구분 |
| 확정 정책·저장 정보 | 자료구조 버전, 확정 정책 버전, 전체 변경 번호 | 미정 정책은 명시적으로 미설정 상태 |

JSON에서 확인된 기존 필드는 손실 없이 보존한다. 위 표는 앞으로 모든 칸을 필수 입력하게 한다는 뜻이 아니다. 추가 필드의 필수 여부는 FRD 결정을 따른다. 기존 엑셀·JSON 전체를 초기 운영 자료로 자동 탑재하는 것은 F14 승인 전 실행하지 않는다.

### 표현과 정밀도

- 업무 일자는 `YYYY-MM-DD` 문자열로 보관해 UTC 변환 때문에 전날로 바뀌는 일을 막는다. 백업 생성·저장 시각은 UTC 시각으로 보관하고 표시할 때 Asia/Seoul로 변환한다. 기존 일별 자료에 주문 시각을 만들지 않는다.
- 돈·수량은 검증된 십진수 문자열로 저장하고 decimal.js로 계산한다. 기존 460.0 등의 숫자는 값이 보존되는 문자열로 변환한다. 계산 도구의 정밀도는 기술 설정이며 금액 반올림·일할 배분 기준은 FRD 정책 결정 후 적용한다. [decimal.js 공식 설명](https://github.com/MikeMcl/decimal.js/)
- `null`은 미입력/해당 없음, `"0"`은 실제 0으로 구분한다. 미입력 의미가 다른 필드는 상태·사유를 함께 보존한다.
- 새 기록ID는 무작위 UUID로 만들고 기존 파일의 ID는 보존한다. 이름 변경으로 판매와 재료의 연결이 끊기지 않게 한다.
- 조회용 색인: 판매 일자·메뉴ID·채널, 비용 일자·분류, 재고 재료ID·일자, 가격 재료ID·적용일. 검색을 위해 이름 변경을 거래ID 변경으로 처리하지 않는다.

### A안의 저장 안전성

IndexedDB에 개별 기록을 저장하고 Dexie의 트랜잭션을 사용한다. 트랜잭션은 여러 저장을 ‘모두 완료하거나 모두 취소’하게 묶는 장치다. 저장 성공은 묶음 완료 후에만 알린다. 파일 읽기·사용자 확인·긴 계산은 트랜잭션 밖에서 수행한다. [Dexie 트랜잭션 안내](https://dexie.org/docs/Dexie/Dexie.transaction())

저장 작업은 기존 변경 번호를 확인한 후 실행한다. 다른 탭에서 자료가 바뀌면 최신 자료를 다시 읽어 사용자에게 충돌을 알려주며 조용히 덮어쓰지 않는다. 수정·삭제·가져오기·복원에 같은 규칙을 적용한다. 이는 공유 사용자 기능 추가가 아니라 같은 브라우저의 두 탭으로 자료가 손상되는 것을 막는 기술 처리다.

브라우저 저장은 사이트 주소와 브라우저 프로필별로 나뉜다. 운영 주소·시험 주소·다른 브라우저는 자동으로 자료를 공유하지 않는다. 데이터 삭제·기기 고장·브라우저 정책에 의한 제거 가능성이 있어 별도 백업이 필요하다. `navigator.storage.estimate()`로 공간을 확인하고 `persist()`를 요청할 수 있으나 성공을 보장하지 않는다. 시크릿 모드나 저장 기능이 막힌 환경을 정상 영구 저장처럼 안내하지 않는다. [IndexedDB 주소별 분리](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API/Using_IndexedDB), [브라우저 저장 한도와 제거](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

FRD에서 저장 버튼·자동 저장은 미정이다. 어느 방식을 선택하든 실제 기록 확정 시 위 저장 경계를 사용한다. 임시 폼을 영구 저장하는 기능은 추가하지 않는다.

## 5. 계산 구현 — FRD 기준 보존

계산 함수는 저장이나 화면 조작 없이 ‘자료 + 확정 정책 → 값 + 상태 + 사유’를 반환한다. 같은 입력이면 같은 결과가 나와야 한다. 화면·양식 미리보기·복원 검사에서 같은 모듈을 사용한다.

| FRD 계산 | 구현 모듈 | 반드시 보존할 점 |
| --- | --- | --- |
| C01 순매출 | 판매 금액 계산 | 할인 단위 미정, 기존 순매출 불일치를 자동 수정하지 않음 |
| C02 원가 | 단가·채널별 레시피 계산 | 구매용량 전체 가격, 포장 전용 재료, 적용일 |
| C03~C04 메뉴 이익·비율 | 메뉴 실적 집계 | 수수료 포함·평균 방식 미정. 매장 순손익과 구별 |
| C05 매장 손익 | 기간 집계 | 비용 이중 반영 방지, 폐기 비용 처리 미정 |
| C06·C08 재고·실사 차이 | 재고 사건 집계 | 시작 재고부터 누적, 실측을 입고처럼 더하지 않음 |
| C07 부족 판정 | 재료 상태 계산 | 안전수량/안전일수 및 평균 기간 미정 |
| C09 월 비용 배분 | 비용 반영 처리 | 이미 배분된 기록에 재배분 금지. 일수 기준 미정 |
| C10 단위 환산 | 기준단위 변환 | g/ml/개와 kg/L/팩 표시 구분 |

반환 상태는 계산 가능·자료 부족·정책 미정·기록 미완료·산출 불가를 구별하고 원인 기록ID를 내부적으로 연결한다. 이 상태값은 개발용 분류이며 새로운 사업 지표가 아니다. ‘미정’을 코드에서 임의 기본값으로 선택하지 않는다. D02가 정해지기 전에는 원가 누락 판매 저장 허용 여부를 확정할 수 없다.

수정·삭제 후에는 저장된 원본에서 관련 결과를 재집계한다. 화면마다 누적 숫자를 따로 더하고 빼면 오차·중복이 생기므로 1차에서는 원본 기록을 계산의 기준으로 삼는다. 원가 스냅샷은 FRD D03에 따라 보존/재계산하며 사용자 결정 없이 최신 가격으로 덮어쓰지 않는다. 동일 날짜 재고 사건 순서·실사 조정 기준은 D05 없이 확정하지 않는다.

2차 전망·발주·확장 기간은 같은 계산 모듈을 사용할 수 있게 분리하지만 1차에 숨겨서 구현하거나 노출하지 않는다.

## 6. 엑셀 가져오기와 양식

1. 내려받은 판매 XLSX를 로컬에서 읽는다. 파일을 서버로 업로드하지 않는다(A안).
2. 파일 확장자뿐 아니라 실제 해석 가능 여부·양식 버전·시트·열을 확인한다.
3. 각 행을 내부 판매 구조로 변환하고 직접 입력과 같은 검증을 실행한다.
4. 원본 행 번호·오류·정상·중복 후보와 반영 예정 건수를 미리보기로 반환한다.
5. 사용자 실행 시 저장 자료 변경 여부를 다시 검사하고, FRD D07에서 선택한 반영 계획을 적용한다.
6. 선택된 기록 묶음은 하나의 저장 트랜잭션으로 반영하고 실제 반영 건수를 표시한다.

‘정상 행만 반영’과 ‘오류가 있으면 전체 중단’은 업무 선택이다. 어느 방식을 선택해도 **선택된 반영 묶음의 저장 중 실패**는 전체 취소해 애매한 부분 저장을 막는 기술안을 제안한다. 덮어쓰기를 승인하면 기존 ID의 값과 판매 영향을 교체한다. 미리보기를 보는 것만으로 저장하지 않는다.

검사 사항:

- 원본 ID·합계키·파일 내용 해시를 보조 정보로 쓰되 해시나 같은 날짜·메뉴·채널만으로 무조건 중복 제거하지 않는다. 동일 파일 재시도와 정당한 추가 판매를 구별할 정책은 D07에 따른다.
- 날짜 문자열·엑셀 날짜값을 분리 해석한다. 엑셀의 1900/1904 날짜 체계를 고려하고 임의 지역 날짜 파싱을 피한다.
- 계산에 쓰이는 칸의 엑셀 수식은 실행하지 않는다. 필수 입력칸의 수식은 오류로 안내하는 기술안을 제안해 오래된 캐시값을 실제 입력처럼 사용하지 않는다.
- 외부 링크·매크로·셀 문자열을 실행하지 않는다. 파일 원문을 HTML로 화면에 삽입하지 않는다.
- 파일 바이트·행 수·열 수·해석 시간을 제한하고 압축된 XLSX가 지나치게 커지는 경우 중단한다. 한도 값은 실측 후 D07로 결정한다. 10MB·CSV 지원은 확정하지 않는다.
- 큰 파일 해석은 Web Worker로 분리한다. 별도 계산 작업이므로 화면의 취소·오류 안내가 멈추지 않게 한다. 파일이 바뀌거나 작업을 취소하면 이전 미리보기 결과를 적용하지 않는다.

양식 생성은 SheetJS로 열 이름·입력 설명·단위를 포함한 XLSX를 만든다. 예시가 실제 판매로 가져와지지 않게 설명과 입력 영역을 구별한다. 기존 전체 운영 XLSX를 판매 양식으로 취급하지 않는다. 초기 전체 자료 이전 여부는 F14로 남긴다.

## 7. 백업·복원·자료구조 변경

### 백업 형식 기술안

JSON을 추천한다. 엑셀보다 여러 종류의 자료·연결·정책을 손실 없이 담기 쉽다. FRD D09에서 형식을 선택하기 전까지 제안 상태다.

백업은 형식 식별자, 자료구조 버전, 앱 버전, 생성 시각, 자료 기간·출처·금액 기준, 저장 변경 번호, 각 기록 배열, 확정 정책을 포함한다. 분석 결과 캐시는 기준 자료로 사용하지 않고 원본에서 다시 계산한다. 기존 제공 JSON은 앱 백업 형식과 구별하고 승인된 이전 절차 없이 복원 파일로 인정하지 않는다.

백업 시 읽기 트랜잭션으로 같은 시점의 기록 묶음을 얻은 뒤 파일을 만든다. SHA-256 해시를 포함할 경우 정해진 방식으로 정렬·직렬화한 본문만 해시한다. 해시는 손상 확인용이며 암호화나 작성자 인증이 아니다. 생성 실패를 성공으로 안내하지 않고 다운로드가 실행되었다는 상태와 실제 파일 보관을 구별한다.

### 복원 기술안

파일 해석 → 버전·필수 구조·ID 연결·금액/수량·정책 검사 → 복원 내용과 영향을 보여주기 → 사용자 실행 → 저장 트랜잭션 → 새 자료로 재계산 순서를 따른다. 파일 검사 중 기존 저장소를 비우지 않는다. 사용자 확인 사이에 자료가 바뀌면 영향 검사를 다시 한다.

전체 교체 또는 병합은 D09 미정이다. 교체가 선택되면 전체 교체를 한 저장 묶음으로, 병합이 선택되면 승인된 중복 정책에 따른 변경 묶음을 저장한다. 실패 시 기존 자료를 유지한다. 병합 정책을 설계하기 전에 병합 버튼을 제공하지 않는다. 복원 전 백업 다운로드 여부도 D09에 따라 정하며 자동 백업 기능을 추가하지 않는다.

### 앱 업데이트와 버전

저장소·백업 자료구조 버전을 앱 코드 버전과 분리한다. 구조 변경은 검증된 변환을 트랜잭션으로 수행한다. 지원하지 않는 미래 버전은 열거나 덮어쓰지 않는다. 변환 실패 시 원본을 유지하고 사용자가 백업·복구할 방법을 안내한다.

Vercel에서 이전 코드를 다시 배포하는 것과 매장 기록 복원은 다르다. 새 자료구조로 바뀐 브라우저에 구버전 앱이 접근하면 안전하게 중단한다. 시험 배포에서 기존 버전 백업과 저장소의 업그레이드·재계산을 검사한다.

## 8. 시안 구현 방법

시안 HTML은 디자인 참고로 활용하고 React 컴포넌트로 옮긴다. 기존 인라인 스크립트·onclick·고정 샘플 숫자·가짜 완료 알림을 운영 코드로 그대로 가져오지 않는다. 시안의 Tailwind CDN과 외부 폰트 호출은 빌드된 CSS·로컬 아이콘·글꼴 또는 시스템 글꼴로 대체한다.

| 시안 | 구현 화면 | 반영할 점 |
| --- | --- | --- |
| _1 | 기간별 실적·손익 | 합의된 기간·지표와 누락 상태만 연결. 예상·POS·시간대·주문·손익분기점은 보류 |
| _2 | 재료·재고 | 입고/폐기/실사 입력, 추정·실측 구분. 안전수량·20%·2% 고정 기준을 넣지 않음 |
| _3 | 판매 관리·XLSX 가져오기 | 영수증 방식에서 확정된 일·메뉴·채널 합계 구조로 연결. FRD의 미리보기 순서 유지 |
| _4 | 메뉴 수익성·원가 상세 | 실적 원가와 현재 기준 참고를 구분. 분류·목표·자동 권고 미추가 |
| _5 | 비용 관리 | 기존 자료 누락칸 보존. 배분·월 템플릿을 확정 정책처럼 구현하지 않음 |
| 본문 시안 없음 | 기초 관리·저장·백업·복원·판매 직접 입력 | 기존 디자인 요소를 재사용해 필수 기능의 입력·확인·오류 상태 구성 |

실제 지원하지 않는 버튼·메뉴는 동작하는 것처럼 두지 않는다. 보류 기능의 숨김/안내 표현은 D10 결정을 따른다. ‘클라우드 정상’, ‘백업 최신’은 실제 기능·상태가 없으면 표시하지 않는다.

넓은 표는 가로 스크롤을 제공하고 숫자·단위를 함께 표시한다. 모바일에서 열이 사라져 필수 정보가 누락되지 않게 한다. 입력칸의 이름, 키보드 조작, 모달 초점 이동·닫기, 색 외에 텍스트 오류 안내를 적용한다. 시안 이미지의 모달·표 잘림을 그대로 재현하지 않는다. 새로운 분석 차트를 추가하지 않는다.

## 9. 개인정보·매장 정보 보호

- A안에서 판매·비용·재고·파일 내용은 브라우저에서 처리하고 Vercel/GitHub로 전송하지 않는다. 다만 사이트 접속 요청의 IP·접속 정보 등은 호스팅 서비스에서 처리될 수 있으므로 ‘어떤 정보도 외부로 가지 않는다’고 안내하지 않는다.
- 고객 개인정보, 직원 주민번호·계좌번호 등은 이 프로그램의 요구사항이 아니다. 기존 메모·지급처에 포함될 수 있는 민감한 내용도 불필요하게 수집하지 않고 로그·오류 메시지에 원문을 남기지 않는다.
- GitHub에는 코드·문서·안전한 가상 검사 자료만 보관한다. 실제 매장 데이터·백업·비밀번호·API 키는 커밋·정적 배포 파일에 포함하지 않는다. 비공개 저장소를 권장하되 비공개만으로 모든 자료를 안전하게 공개할 수 있는 것은 아니다.
- 프로그램과 라이브러리를 자체 배포 파일로 제공하고 제3자 분석·광고·원격 오류 수집을 기본 추가하지 않는다. 외부 폰트 요청도 줄인다.
- React의 기본 문자 표시를 사용하고 파일·메모를 HTML로 실행하지 않는다. CSP(허용한 코드·연결만 실행하는 정책), MIME 형식 보호, 불필요한 브라우저 권한 차단과 HTTPS를 적용한다. A안은 외부 자료 업로드 경로를 만들지 않는다.
- 브라우저 내부 저장은 암호화 금고가 아니다. 같은 컴퓨터·프로필을 사용하는 사람이나 악성 확장 프로그램·삽입된 코드가 자료를 볼 위험이 있다. OS 계정·화면 잠금과 기기 접근 관리가 필요하다. 단순 프런트엔드 비밀번호를 보안 인증으로 취급하지 않는다.
- 백업 파일도 모든 매장 기록을 포함한다. JSON 추천안은 평문이므로 안전한 개인 저장 위치에 보관해야 한다. 파일 암호화·앱 잠금 기능은 승인 없이 추가하지 않으며 필요하면 별도 결정한다.
- 운영 사이트와 시험 배포는 별도 주소·자료를 사용한다. 시험 배포에 실제 백업을 복원하지 않고 가상 자료로 검사한다.

이는 기술 보호 설계이며 개인정보 법률 준수 인증을 의미하지 않는다. 실제 수집 정보가 늘어나면 보호 요구를 다시 검토한다.

| 기간·메뉴 결과 조회 | 1초 이내 | 기준 규모 자료, 저장소 초기 읽기 이후 |
| 기록 저장과 결과 갱신 | 1초 이내 | 단일 기록 변경, 동일 기준 자료 |
| 파일 검사·복원 | 기준 규모에서 5초 이내 목표 | 기기별 측정. 초과 시 진행/취소·안내가 가능해야 함 |

속도 수치는 보장이 아니다. 검사 기기·브라우저·파일 크기와 실제 결과를 기록한다. 열/행 폭·파일 복잡도도 영향을 준다.

최적화: 조회 색인, ID별 레시피/가격 사전, 변경 번호에 따른 집계 캐시 무효화, 표 페이지 표시, XLSX 도구의 필요 시 로딩을 사용한다. 과거 판매를 수정하면 변경일 이후 재고 캐시도 무효화한다. 복원 후에는 모든 계산 캐시를 버린다. 캐시 때문에 오래된 계산이 저장 성공처럼 보이지 않게 한다. 통째로 저장하는 localStorage나 모든 기록 DOM 렌더링을 피한다.

## 11. 오류 대응·검사·GitHub/Vercel 배포

### 오류 대응

| 오류 | 대응 |
| --- | --- |

| 원가·재고 근거 누락 | 해당 결과의 산출 상태·근거 누락 안내. 0으로 대체하지 않음 |

| 화면 또는 계산 오류 | 오류 경계를 통해 다른 화면·백업 접근을 가능한 범위에서 유지. 오류 코드만 남기고 매장 원문 로그 제외 |

업무 날짜가 바뀌어도 미마감 판매를 자동 확정하지 않는다. 네트워크 단절과 저장 실패를 구별한다. A안 계산은 로컬에서 가능하지만 새로고침·첫 접속의 완전 오프라인 사용은 보장하지 않는다. PWA·서비스워커 기능은 승인되지 않아 1차에 추가하지 않는다.

### 필요한 검사

- TypeScript 타입 검사·정적 검사·운영 빌드 성공.
- 합의된 C01~C10의 정상 값·0·미입력·단위·가격 적용일·채널 경계 검사.
- 판매 변경으로 매출·이익·재고가 한 번씩 반영되는 연결 검사.
- 월 계획/일별 비용 중복, 원가 미확인, 미래·부분 기간, 실사 전후 변경의 합의 정책 검사.
- 저장 실패·가져오기 재시도·복원 실패·버전 변경·두 탭 충돌 검사.
- 실제 브라우저에서 입력 → 수익성 → 손익/잔량 → 수정·삭제 → 다시 열기 → 양식 가져오기 → 백업·복원 검사.
- 기준 가상 규모의 성능 측정과 모달·표 잘림/키보드 접근 검사.

가상 IndexedDB 검사만으로 브라우저 실제 저장을 검증했다고 보지 않는다. 운영에 사용할 브라우저를 D09에서 확인하고 최소 그 환경에서 파일·저장·복원 흐름을 검사한다. 서로 다른 브라우저 저장소가 별개라는 점도 안내한다.

### GitHub 보관과 배포 순서

1. GitHub 저장소에는 코드·잠금 파일·요구사항·검사·설정 예시를 저장한다. `.gitignore`에 실제 자료·백업·환경 비밀값·빌드 산출물을 제외한다. 검사 가상 자료는 별도 구분한다.
2. 변경별로 타입·핵심 자동 검사·빌드를 실행한다. 기본 명령은 `npm ci`, `npm run typecheck`, `npm run test`, `npm run build`로 프로젝트에 정의한다. 실패한 변경을 운영 배포하지 않는다.
3. Vercel에서 GitHub 저장소를 연결하고 Vite, 빌드 `npm run build`, 출력 `dist`, 고정 Node 버전을 설정한다. [Vercel의 GitHub 연동](https://vercel.com/docs/git/vercel-for-github)
4. 시험 배포에서 가상 자료로 브라우저 검사를 한다. 운영 배포는 검사된 변경만 승인된 운영 브랜치에서 수행한다. 이번 문서에서 브랜치 이름·저장소 공개 여부·주소를 임의 확정하지 않는다.
5. 운영용 주소를 하나로 유지한다. 주소 변경 전 백업하고 새 주소에서 승인된 복원 절차를 수행한다. 배포마다 달라지는 시험 URL을 매장 운영 저장 주소로 사용하지 않는다.
6. 배포 후 HTTPS·접속·핵심 흐름·파일·다시 열기·복원 결과를 확인하고 코드 버전·검사 결과·복구 방법을 남긴다. 코드 롤백과 데이터 복원을 구분한다.

프런트엔드에 전달되는 설정값은 사용자에게 보일 수 있다고 전제한다. A안에는 DB 비밀키가 필요 없으며, GitHub/Vercel 배포 토큰은 코드·화면·백업에 넣지 않는다.

## 12. 여러 기기 서버 저장을 선택할 경우

B안은 현재 확정되지 않았으므로 기본 구현에 추가하지 않는다. 선택되면 저장소를 서버의 관계형 데이터베이스로 바꾸고 저장 API·인증·매장별 접근 제한을 함께 설계해야 한다. 데이터베이스는 판매와 재료의 연결을 보관하는 서버 저장소다. 인증은 접속자가 기록 주인인지 확인하는 장치다.

화면·검증·계산 코드는 유지할 수 있게 저장소 인터페이스를 분리한다. 서버는 모든 입력을 다시 검증하고 DB 트랜잭션·중복 요청 방지·권한 검사를 수행해야 한다. 사용자별 기록을 공개 API로 노출하거나 브라우저 비밀값 하나로 보호하지 않는다. 승인된 사용 범위를 넘는 직원 권한·여러 매장 기능을 함께 추가하지 않는다.

DB·인증 서비스 공급자, 지역, 비용, 보관/삭제·백업, 서버와 브라우저의 계산 책임, 로그인 흐름은 별도 기술 설계 대상이다. 공급자를 선택하기 전에 한 명이 여러 기기에서 쓰는지 여러 사람이 공유하는지 확인한다. B안 선택 시 이 TRD의 A안 저장·보안·배포 부분을 갱신하며 완성 설계라고 간주하지 않는다. 4시간 내 가능성도 다시 검토한다.

## 13. 4시간 목표와 구현 착수 조건

PRD의 30분 기획·20분 화면 설계·125분 개발·40분 검사·25분 배포 배분을 유지한다. TRD 작성 때문에 검사·배포 시간을 줄이거나 기능을 임의 제외하지 않는다.

A안, 사용할 자료 준비, 계정/배포 연결 준비, 핵심 FRD 정책의 합의가 끝난 경우에 이 작은 구조로 구현을 시도한다. 모든 정책·누락 시안·자료 정리가 남은 현재 상태에서 전체 구현을 4시간 내 보장할 수는 없다. 시간이 부족하면 사용자와 범위를 조정하고 필수 흐름·자료 안전 검사는 유지한다.

착수 전 확인:

- D02: 원가 누락 판매 저장·부분 결과 표시.
- D03~D06: 원가·수수료·비용·실사·부족 판단 기준.
- D07~D08: 양식·오류/중복·기간·마감 처리.
- D09: 사용 기기·브라우저 저장/서버 저장, 백업·복원 방식.
- D10: 시안의 추가 기능 처리와 누락된 필수 입력/백업 화면.
- GitHub/Vercel 계정 접근, 실제 사용에 맞는 요금제, 운영 주소.

지금 확인 중인 질문은 D09 사용 환경 하나다. A: 같은 컴퓨터·같은 브라우저에 저장(4시간 목표에 추천), B: 여러 기기에서 서버 저장. 앞서 FRD의 D02 질문은 미정으로 보존하며 이번 기술 설계에서 답을 대신 정하지 않는다.
